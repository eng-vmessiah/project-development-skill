# Custom Feature Templates

`pd init` accepts a template directory:

```bash
pd init my-feature --template-dir /path/to/templates
```

The directory may contain any of these files:

- `SPEC.md`
- `PLAN.md`
- `CONTEXT.md`

Missing files fall back to the built-in templates. The literal `{{feature}}` in a
template is replaced with the feature name; a template without the placeholder is
used verbatim.

## Example

```text
templates/
├── SPEC.md
└── CONTEXT.md
```

`templates/SPEC.md`:

```markdown
# SPEC.md - {{feature}}

## Requirements
- [ ] Describe the first requirement

## Constraints
- Constraint 1
```

`templates/CONTEXT.md` may be omitted: `PLAN.md` and `CONTEXT.md` come from the
built-ins while `SPEC.md` comes from the directory.

## Validation

The command fails before creating the feature when:

- the directory does not exist;
- none of the three recognized files is present;
- a recognized path is a symlink or is not a regular file;
- a template cannot be read as UTF-8.

`STATE.md`/`STATE.json` are still generated by PD; they are not customizable.
Creating the feature directory is the first side effect, so a rejected template
directory leaves no partial feature behind.

## What this does not do

- It does not add new lifecycle phases or gates.
- It does not change validation semantics; a custom template must still produce a
  SPEC/PLAN/CONTEXT that `pd validate` can read.
- It does not install templates globally; pass the directory on each `init`, or
  wrap the command in your own project script.
